### M1 — tools + `HTNToolsOnly` (gate passed)

Built, in order: `harness/tools/features.py` (thin `diagnose()` wrapping
`gpc.engine.{grid,loop,traversal}`), `harness/tools/incrementality.py`, `harness/tools/siblings.py`,
`harness/tools/headroom.py`, `harness/tools/sizing.py`, `harness/tools/precheck.py`,
`harness/htn/tasks.py` (minimal Task/Method/MethodRegistry scaffold), `harness/htn/methods.py`
(M_Reprice, M_Sibling, M_Budget, M_CompetitorCut, M_Base), `harness/policy.py`
(`HTNToolsOnly`, plus `HTNHarness` as a thin wrapper that is identical to `HTNToolsOnly` until
M2/M3 add the LLM leaves).

**Incrementality (`tools/incrementality.py`).** Regresses `organic_units` (from
`sku_city_daily`, public/observed — never `world.truth`) on same-day `ad_orders` split by keyword
type, with joint SKU×city + day-of-week fixed effects (`numpy.linalg.lstsq`). First attempt used
separate `sku_id` and `city_id` dummies (additive, not joint) and got the ordering wrong
(`generic` beta came out *positive*, `competition` more negative than `generic` — opposite of
E1). Fixing the FE to a single joint `sku_id x city_id` dummy column fixed it: on dev-seed-7
warm-up data, pooled beta is brand −0.55 < generic −0.36 < competition +0.12, i.e. ι_brand <
ι_generic < ι_competition as E1 predicts (magnitudes differ from the E1 report's −0.88/−0.50/≈0,
which were read off the *baseline's* 42-day trajectory, not raw 28-day warm-up — expected, and the
ordering is the thing both the plan and the test care about). Per-SKU betas are shrunk toward the
pooled type beta by `orders / (orders + 25)`, same convention as `gpc.engine.grid`/`loop`.
Deferred: an explicit `organic_rank`-based prior (E8) — noted in the module docstring, not built,
since the type-level shrinkage is already directionally doing similar work and this wasn't
blocking the M1 gate.

**Siblings (`tools/siblings.py`).** Implements the handoff's correction directly: sibling
collision does not inflate price (clearing prices come from external competitors in
`gpc.market`), so the cost is a futile follower raise and a possibly-wrong leader, not
"paying to outbid yourself". `leader_score = conv1 x ASP x ι` (incremental revenue per
impression); `followers_to_hold` returns the (campaign_id, keyword_id) pairs that should never be
raised because a sibling already holds >=80% of slot 1 there. On dev seed 7: 100/110 cells and
40/50 markets are contested, matching the plan's E2 evidence and the `A2-tests-and-scenarios.md`
test spec's "40/50" number exactly.

**Headroom (`tools/headroom.py`).** Converts the ROAS-floor-is-window-cumulative fact (E9) into a
per-run spend allowance: `headroom_cum = max(cumulative_eval_revenue / (floor*(1+margin)) -
cumulative_eval_spend, 0)`, spread over the coming run's 7 days, then a fraction of that per
`params.run_allowance_frac[run]` (front-loaded schedule in `default.json`). At run 1 this is 0
(no post-warmup cumulative data exists yet) — correct, since there is nothing banked to draw on
yet; `gpc.guardrails`'s own G8 is the actual hard floor enforcement regardless, so this tool only
shapes how aggressively the harness *tries* to spend, not whether it's allowed to.

**Sizing (`tools/sizing.py`).** Implements the handoff's Lagrangian knapsack, but scoped to raise
candidates only (bid raises + budget raises); cuts (sibling-follower holds, competitor misses) are
unconditional and handled directly by the methods, not by this budget. For a given `mu`, each
(campaign_id, keyword_id, action_type) group's best option maximises `iota * delta_rev - mu *
delta_spend`; binary search picks the smallest `mu` whose total `delta_spend` still fits the run's
headroom allowance. `delta_spend`/`delta_rev` always come from `gpc.guardrails.project_actions`
(read-only import), so sizing's estimate matches exactly what guardrail G8 will project.
**Deviation from the plan's exact formula** (`iota*delta_rev - mu*(floor*delta_spend -
delta_rev)`): simplified to the more standard knapsack form above after the original formula's
derivation wasn't recoverable from the handoff note alone; G8 is the actual safety net either way,
so this is a shaping heuristic, not a correctness-critical piece. Worth revisiting if the lift
numbers look sizing-bound once `harness_eval` is built.

**Precheck (`tools/precheck.py`).** Mirrors G0/G3/G4/G5/G7 using `gpc.guardrails`'s own exported
constants. `tests/harness/test_tools.py::test_precheck_matches_guardrails_on_randomized_actions`
property-tests it against `apply_guardrails` directly (30 randomized bid/budget raises per run) —
this is the test that actually matters, not the docstring.

**Bugs hit and fixed while wiring `HTNToolsOnly.recommend` (`harness/policy.py`):**
1. `tools/sizing.py::project_candidates` called `gpc.guardrails.project_actions` with
   `diag.pacing` (plain `campaign_pacing(obs)`, not indexed), but `project_actions` does
   `pacing.loc[a.campaign_id, ...]` — needs `.set_index("campaign_id")` first, same as
   `apply_guardrails` does internally before calling it. `KeyError: 'C-S1-DEL'` on the first
   `increase_cpm` candidate it tried to project. Fixed by indexing in `project_candidates` itself.
2. `sizing._value(mu, iota, ds, dr)` used Python's builtin `max(ds, 0.0)` where `ds` is a pandas
   Series inside the vectorized `.assign(...)` call in `pick()` — `ValueError: truth value of a
   Series is ambiguous`. Fixed with `np.maximum`.

### M2 — LLM layer (done, tested, live-verified)

Built `harness/llm/{client,providers,replay,meter,faults}.py` and `harness/leaves/{schemas,run}.py`:

- **`client.py`** — `LLMClient` protocol (`complete_json(system, user, schema, timeout) ->
  (dict, Usage)`) and a `Usage` dataclass (`calls`/`tokens_in`/`tokens_out`/`cost_usd`/
  `wall_clock_s`, with `__add__` for accumulation).
- **`providers.py`** — `OpenRouterClient`/`OpenAIClient` (share an `OpenAICompatClient` base,
  since both speak the `openai` SDK, differing only in `base_url`) and `AnthropicClient`. Lazy
  `import openai`/`import anthropic` inside `__init__`, so importing this module needs neither
  package unless that provider is actually selected. JSON enforcement: a system-prompt
  instruction plus one repair retry (resend with the parse error) on every provider — not just
  OpenAI's native `response_format`, since OpenRouter can route to a model that doesn't support
  it. No `temperature` is set anywhere (per the open item: newer Claude models reject it).
  `build_provider(provider, model)` reads `LLM_PROVIDER`/`LLM_MODEL` and routes; `"none"` returns
  `None` (tools-only).
- **`meter.py`** — wraps any `LLMClient`, accumulates `Usage`, prices it from a small
  substring-matched table (`claude-opus/-sonnet/-haiku`, `gpt-5`, `gpt-4o(-mini)`, else a flat
  fallback of $3/$15 per M tokens in/out), and raises `BudgetExceeded` the moment cumulative cost
  for the run passes `params.llm_max_usd_per_run`.
- **`replay.py`** — `ReplayClient`, the outermost layer leaves actually call. Cache key =
  `sha256(leaf, prompt_ver, system+user text, schema_ver, replicate)`, one JSON file per key
  under `LLM_CACHE_DIR` (`llm_cache/`, gitignored except a deliberately committed set). `off`
  never reaches it (`leaf()` short-circuits on `llm=None` first); `record` calls-and-caches (a
  second call with the same key is a cache hit, not a second charge); `replay` is cache-only and
  raises `FileNotFoundError` on a miss (reproducibility must fail loudly, not silently go live);
  `live` always calls and never touches the cache.
- **`faults.py`** — `FaultInjectingClient`, keyed on `FAULT_INJECT`: `timeout`/`exception` raise;
  `budget` raises `BudgetExceeded` without calling the inner client; `malformed` returns a
  response with none of the expected fields (so pydantic validation fails outright); `out_of_range`
  returns every property from the JSON schema filled with an extreme value (`1e12` for
  numbers, a 10k-char string, `True` for booleans) — present but absurd, which is the case that
  should get *clipped*, not defaulted.
- **`leaves/schemas.py`** — pydantic v2 models for L1 Value, L2 Shock, L3 Sibling, L4 Explore,
  L5 Ledger, L6 Review. Each has >=1 field with no default, so a response missing it (e.g. the
  `malformed` fault's `{"_fault": "malformed"}`) raises `ValidationError` inside
  `validate_and_clip` and returns the caller's default; numeric fields use a `mode="before"`
  field validator that clips into range instead of raising, so `out_of_range` produces a clipped
  object, not a default. `validate_and_clip(schema_cls, data, default, known_ids=, id_field=)`
  also drops (falls back to default on) an id field outside a supplied known-id set.
  **None of these are wired into `harness/htn/methods.py` yet** — that is M3's "methods wired with
  the LLM" step, deliberately not started this session (see below).
- **`leaves/run.py`** — `leaf(llm, name, system, user, schema_cls, default, ...)`: the one call
  site a future M3 integration will use. `llm=None` (meaning `LLM_MODE=off` or `LLM_PROVIDER=none`)
  returns the default immediately, no attempted call at all — this is the single no-LLM code path,
  not a second one bolted beside the fault/replay machinery. Any exception from the call is caught
  broadly and absorbed into a `"default"` outcome for the trace; this is the first (per-leaf) of
  the two fail-soft layers, the second being `HTNToolsOnly`/`HTNHarness`'s own
  fallback-to-baseline in `policy.py`.
- **`harness/llm/__init__.py::build_llm_stack(params)`** — the factory that reads `.env` (loads
  it once via `python-dotenv`) and assembles provider -> `FaultInjectingClient` ->
  `Meter` -> `ReplayClient` into the single client a leaf is handed. Returns `(None, mode)` for
  `mode == "off"` or an unconfigured/`"none"` provider.

All of this is implementation to spec from the plan's module map with no deviations worth
flagging (unlike M1's sizing simplification).

### Session 2026-10-02, part 3 — M3: leaves wired into methods, S1-S10

**Decided which SG gets a leaf, and why, before writing any prompt:**

- **SG3 sibling tie-break (L3)** — only when the top two `leader_score`s in a contested market are
  within 10% of each other. A clear mechanical win should not be second-guessed; a genuine
  near-tie is exactly where the mechanical score (conv x ASP x iota, all themselves estimates) is
  noisiest and a broader read might help.
- **SG5 shock-surge raise (L2 Shock)** — a cell flagged `shock_reach` (new `tools/shocks.py`,
  z-scores vs a 21-day baseline, min-abs-diff guarded — see the false-positive fix below) that
  isn't already being raised by M_Reprice gets a confirm-then-raise path, so a demand surge
  doesn't have to wait a full run for the mechanical verdict to catch up (E4).
- **SG2 raise-size trust (L1 Value)** — only for tier-B CLEARS raises. Tier A is strong evidence
  (no need to second-guess); tier C never reaches a raise mechanically in the first place (held).
  Dampens or extends the mechanically-chosen raise's *size*, never invents a new target bid.
- **SG6 explore (L4 Explore)** — the only way a THIN cell is ever touched at all; capped by both
  `params.explore_max_thin_cells` (count) and `params.explore_spend_cap_inr_day` (rupees),
  disabled by default (`explore_enabled: false` in `default.json`) since it's a pure cost with
  uncertain payback until `harness_eval` can measure it.
- **L6 review (veto-only, L2 depth only)** — one pass over this run's raises above
  `params.llm_review_threshold_inr` of projected daily spend. Can only drop the large raises it
  was shown; cannot touch cuts, budget raises, or anything below the threshold.
- **Explicitly not wired this session**: L5 Ledger (`memory/ledger.py` is M5 — a hypothesis needs
  somewhere to be checked against next run's realised numbers, which doesn't exist yet).

**New tool: `harness/tools/shocks.py`** (z-scores of slot-1-eq reach/CPM vs a 21-day baseline, OSA
z-score, `own_action_confound` flag). **Bug caught before it reached a test**: the first version's
`_zscore` had a `baseline.std() < 1e-6` fallback that returned `sign(diff) * 5.0` for *any*
nonzero difference against a near-constant baseline — on dev warm-up data this flagged 21 of 83
cells as an OSA shock, because OSA is naturally near-constant and any float-level wobble tripped
it. Fixed by requiring the difference to clear a `min_abs_diff` floor (5% of the baseline mean for
reach/CPM, 5 percentage points for OSA) before the near-constant-baseline branch fires at all;
re-ran and got 1 reach shock / 0 CPM / 0 OSA on the same data — caught this by actually printing
the flag counts before writing a test around them, not by assuming the first version was right.

**Correctness fix (not a bug, a gap against the plan's own test spec): S10.**
`tools/headroom.py`'s front-loaded `run_allowance_frac` schedule (`[0.10, 0.15, 0.20, 0.20, 0.20,
0.15]`) left run 6 — the *last* run, with no run 7 to carry unused headroom into — spending only
15% of the remaining headroom, same as every other run. That's wrong: by definition nothing
carries past the last run, so it should spend the rest. Added a special case: `obs.run >=
N_RUNS` uses `frac = 1.0` regardless of the schedule. `test_s10_...` pins this down directly
(computed on a real 6th-run observation via a 63-day simulation, not a mocked one, since headroom
is a cumulative-window calculation that's easy to get subtly wrong on fabricated inputs).

**`harness/htn/llm_methods.py`** — `sibling_tiebreak`, `shock_raises`, `adjust_raise_sizes`,
`explore_candidates`, `review_veto`. Each degrades to a no-op when `llm is None` (`leaf()`'s own
behaviour, not re-implemented here) — this is what keeps `HTNHarness(llm=None)` byte-identical to
`HTNToolsOnly`, verified directly (not just asserted): ran both on dev seed 7 for 2 runs and
diffed `summarize()` output field-by-field — identical. Also verified depth="L1" with a
hand-rolled `MockLLM` end-to-end through `simulate()` (2 runs, no exceptions, no fallback), then
again with the mock forced to answer "yes" to every judgment (`explore=True`, `is_shock=True`,
`direction="surge"`) to confirm the new candidate paths actually produce shaped actions (3
`M_Explore` actions, capped at `explore_max_thin_cells`) rather than silently no-opping.

**`harness/leaves/prompts/{L1_value,L2_shock,L3_sibling,L4_explore,L6_review}.v1.md`** and
`harness/leaves/render.py` (loads a `<!-- system -->`/`<!-- user -->`-delimited `.md`, renders the
user half with `str.format`). One correction made while writing `L6_review.v1.md`: the first draft
told the reviewer it could veto a *subset* (`concerning_action_ids`) of the large actions shown to
it, but `L6Review`'s schema (deliberately, for simplicity) only has `veto: bool` — the prompt was
promising a capability the code doesn't have. Rewrote it to say a veto drops everything shown in
that call, nothing more, before this became a real mismatch between what the model is told and
what `review_veto()` actually does with its answer.

**`harness/policy.py` rewrite.** `_harness_recommend(obs, params, llm, action_log)` now does the
full L1/L2 pipeline when `llm is not None` and `params.depth != "L0"`, else delegates straight to
`_tools_only_recommend` (one function call, not a parallel reimplementation — this is *why*
`HTNHarness(llm=None)` is identical to `HTNToolsOnly`, not just observed to be). `HTNHarness` now
keeps `self._action_log: dict[(campaign_id, keyword_id), [day, ...]]`, appended to after every
`recommend()` call, and passed into `detect_shocks(..., own_action_days=...)` next run — this is
what lets the harness tell "the market shocked" apart from "I changed this bid three days ago and
I'm looking at my own aftermath" (E5), using the harness's own decision history rather than trying
to infer it from the data, which isn't reliably possible without it.

**S1-S10 scenario tests** (`tests/harness/test_scenarios.py`, 11 tests — S9 split into two: the
coarse whole-policy fallback and the finer per-leaf absorption, since the plan's one line covers
both of the fail-soft doc's three levels). First run: 10/11 passed immediately; **S2 failed** —
written initially as "a competitor cut must be >= 20%", but the dev fixture's competitor MISSES
cells all happen to have a miss streak >= 3 days already, so a streak-based framing would have
been fixture-lucky, and a fixed-20%-threshold framing just happened not to be hit by whichever bid
step was best-dROAS that day. Rewrote to assert the actual structural claim instead: the cut
target equals the best-pred_droas option among bids below the live one, with no ladder/max_cut
check in the code path at all — true regardless of streak or magnitude, and it's the real
difference between `M_CompetitorCut` and `M_Base`. Logged the reinterpretation (and S8's, a
smaller one: "retreat" means "don't chase a price shock with a raise", since there's no mechanical

**Mid-turn: a parallel review session (the user is running one alongside this one) sent its
findings.** Read carefully and verified each one directly against this code rather than taken on
trust — all turned out to be real:

1. **`M_CompetitorCut`'s core premise was backwards.** Its docstring and reason string both
   claimed competitor keywords have "~0 incrementality" (E1), so cutting them fast costs ~0
   offtake. E1 actually says beta_competition ~0, which means iota_competition ~1 — competitor
   keywords are the **most** incremental lever in the portfolio (brand iota ~0.12-0.20 is the low
   end, because a brand-keyword searcher would likely have found Aurel organically anyway; a
   competitor-keyword searcher would not). The handoff's "faster competitor cuts" lever was
   reading competitor's poor *direct* ROAS (goal_droas ~1.6 vs brand's 9.0), a different axis
   entirely — a low-dROAS keyword can still be highly incremental, and this one is. Cutting
   competitor spend fast is the *expensive* move, not the cheap one. **Fix**: removed
   `m_competitor_cuts` entirely (not renamed, not reworked — the premise was wrong, so the
   special case doesn't get to survive in a patched form); competitor MISSES cells now take the
   same ladder-paced `m_base_cuts` path as brand/generic, same as everything the original gaps
   analysis didn't specifically flag. Updated `harness/htn/methods.py`'s module docstring with
   the full correction, `harness/policy.py` (removed the now-dead `comp_cuts`/`m_competitor_cuts`
   wiring in both `_tools_only_recommend` and `_harness_recommend`), and rewrote S2's scenario
   test (`test_scenarios.py`) from "competitor cuts skip the ladder" to a regression guard that
   competitor MISSES cells go through the *same* path as everything else — i.e. a test that would
   fail again if this exact bug ever came back. This was caught by a human/review process reading
   `harness_eval/probes.py`'s own E1 output, **not** by any test in this repo — every existing
   test checked that the (wrong) special case behaved consistently with its own wrong premise,
   which a self-consistent wrong premise will happily keep passing forever.

2. **Replay cache key didn't include the model.** `harness/llm/replay.py::cache_key` hashed
   `(leaf, prompt_ver, system, user, schema_ver, replicate)` — switching `LLM_MODEL` while
   reusing a cache directory could silently replay a *different* model's cached response as if it
   were the newly configured one. Fixed by adding `model` to the key (and to the cached JSON
   file's metadata). A cache recorded before this fix has a different key under the new scheme and
   will simply miss, not silently misattribute — the safe failure mode.

3. **A cache hit never credited the wrapped `Meter`'s running total.** `ReplayClient`'s
   `replay`-mode and `record`-mode-cache-hit paths returned the cached `Usage` straight to the
   caller without ever touching `self.inner.usage` — so `Meter.usage` (what `usage_of()`/the trace
   both report) only counted *live* calls, undercounting cost for anything served from cache. This
   is exactly what the parallel session's OpenRouter-dashboard-vs-matrix-report comparison would
   have surfaced on a real `LLM_MODE=replay` run (never actually run this session, so this was
   caught by code reading, not by observing a wrong number). Fixed with
   `ReplayClient._credit_cached_usage()`, called on every cache-hit path, duck-typed via
   `hasattr(self.inner, "usage"/"run_usage")` so it degrades gracefully when `self.inner` isn't a
   `Meter` (e.g. a bare mock in a test).

4. **The per-run LLM budget was actually a per-simulation budget.** `Meter.max_usd_per_run` was
   checked against the same `self.usage` that accumulates for the whole lifetime of the `Meter`
   object — and `HTNHarness` builds one `Meter` lazily, once, reused across every run in a
   `simulate()` call. So `LLM_MAX_USD_PER_RUN` was silently enforced once across an entire 6-run
   simulation, not per run as the name promises. Fixed by splitting `Meter.usage` (lifetime,
   unchanged semantics — still what `usage_of()` reports) from a new `Meter.run_usage` (since the
   last `reset_run()`, what the budget check now uses), plus a `reset_run_budget(llm)` helper
   (same chain-walking pattern as `usage_of`) that `HTNHarness.recommend` now calls at the start
   of every run.

**A fifth bug found while fixing #3-4, not reported by the review**: `leaf()` itself dropped
`usage` to `None` whenever validation failed (`outcome == "default"`), even though a response that
came back and failed validation still made a real, billed call. Fixed alongside the others —
`usage` (and the raw pre-validation `raw_response`, now also surfaced for the first time) is
included whenever a call actually happened, not only when it validated cleanly.

**All four + the fifth fix verified with new regression tests**, not just "doesn't crash":
`test_replay_cache_key_is_sensitive_to_model`, `test_replay_cache_hit_still_credits_the_wrapped_meter`,
`test_meter_budget_is_per_run_not_per_lifetime`, `test_reset_run_budget_walks_the_stack_to_the_meter`,
`test_reset_run_budget_is_a_noop_for_none_or_no_meter`, `test_leaf_malformed_response_still_records_usage_and_raw_response`
— each one fails against the pre-fix code (verified by construction: each test asserts the exact
thing the bug got wrong) and passes against the fix. One self-inflicted hiccup while writing
these: an `Edit` call accidentally merged a new test's body with the tail end of the test above it
