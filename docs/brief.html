§2 · The baseline: deterministic grid-path traversal
This is the logic you are trying to beat. Code, data and a viewer that walks through every step for every run and cell are at github.com/sidnuti/grid-path-challenge (link). Open viewer/grid_path_viewer.html first.
1 · GridFrom 28 days of data: CPM, impressions, orders and ROAS for every cell × slot (1/5/9/13) × daypart. Thin evidence is shrunk.
2 · LoopPer cell: clears goal, misses goal, or too thin. Cuts are paced by a patience ladder: 3 / 5 / 7 miss-days allow 10 / 25 / 50% of spend.
3 · TraversalBid first (±5–50% steps), then move money (receiver must earn ≥ 1.2× the source with P > 0.8, one transport LP), then hours.
4 · LedgerDecisions become actions on real levers. Budget raises are sized by how much of a raise the campaign can actually spend.
5 · GuardrailsBid bounds and step size, top slot, stock availability, realisable budget, cell goal, and the portfolio ROAS floor. Mandatory for every policy.
§3 · The task: build an LLM harness that generates better actions
Build a harness around an LLM that produces better campaign actions than the deterministic traversal. To the sandbox, the harness is just a policy: it reads the run's Observation and returns a list of actions. How it gets there is your design. Some shapes it could take:
  • an agent with tools over the observed data and the engine's pieces (grid, verdicts, bid options, projections) that decides cell by cell or campaign by campaign;
  • an LLM that reviews and rewrites the traversal's proposals before they go out;
  • an LLM that forms hypotheses (where is spend not incremental? which thin cells are worth exploring?) while deterministic code sizes the moves.
Deterministic code is welcome as tools. What we need to see is that the LLM is what makes the decisions better. Show it with an ablation: the same harness with the LLM step removed.
Hard rules (breaking one scores as not passing):
  1. Observation only. The harness reads what it is given. Reading the simulator, its scenario files or its hidden parameters, or putting their values into a prompt, disqualifies the submission.
  2. Guardrails stay on. Every action passes the guardrail layer. Do not modify it, the simulator, the runner or the scorer; we score with our copies.
  3. Validated output. LLM output is parsed and checked against the action schema before it leaves the harness. Malformed or out-of-range output must not crash a run.
  4. Reproducible. make score POLICY=… on a clean checkout reproduces your numbers. Report results over at least 3 replicates, because LLM calls are stochastic.
  5. Fail soft. If the LLM errors, times out or exceeds its budget, the run falls back to the baseline. Show that it does.
§4 · How we score it
The dev scenario ships with the repo. We also score on a private eval scenario. It uses the same mechanics and the same kinds of entities, but a different seed, different true response values, and shocks in different places and at different times. A harness that reasons from the data carries over. One tuned to dev's particular numbers does not. Scores are always measured against the baseline run in the same world.
